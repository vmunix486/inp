INP: An INI image format

by vmunix, started on 7/31/26


Summary

INP is an image format that I have thought up of over the course of a week or so. It is an image format that uses INI files, and is very simple in design to make it easy for developers to implement it for all types of operating systems, display methods, and hardware.

The files themselves

A normal INI file looks something like this:

[owner]
name = John Doe
organization = Acme Widgets Inc.
				
[database]
server = 192.0.2.62
port = 143
file = "payroll.dat"

INI files are very simple, they are in the format of variable = string, making them one of the easiest ways to store configuration or settings for programs. Another part of INI files is that they can have sections in them, using the syntax [section].

INP files follow this same convention of variable=string, but there are a few minute differences. One of the first things that differentiate INI files and INP files is that there are only 2 sections in an INP file, the first one is labeled "General" and the second one is labeled "Picture".

Inside of the General section, there is information about the image, such as information about the width and height, as well as info for the picture itself, such as the Name, Creator, and Creation date of the picture, as well as a Note for the image itself, among other things that can go into the General section.

In the "Picture" section, is the actual data for the image itself. The data is in the form of X coordinate, Y coordinate equals color. The color will always be in HTML hex, without a leading "0x" in front of it. There can optionally be Alpha in the color as well, but it needs to be enabled within [General].

Here is an example of a very simple INP file.

[General]
width=3
height=1

[Picture]
x1y1=ff0000
x2y1=00ff00
x3y1=0000ff

When viewed, this picture has, well, 3 pixels horizontally. The one on the left is red, the one in the middle is green, and the one on the right is blue.

This is where simplicity comes from. For the coder, this image format is very simple to write a viewer for, or even a INP maker. As an example for how easy it is to make a viewer for this format, I have made a very simple one in my flavor of Lua, BLua, with Raylib.

local screenWidth = 800
local screenHeight = 600

local file = io.open("image.inp", "r")
if not file then
        io.close(file)
        print("Could not load file")
        os.exit(1)
else
        io.close(file)
end

local img = ini.parse("image.inp")

raylib.SetConfigFlags(FLAG_WINDOW_RESIZABLE)
raylib.InitWindow(screenWidth, screenHeight, "INI image viewer")
raylib.SetTargetFPS(60)

while not raylib.WindowShouldClose() do
        raylib.BeginDrawing()
                raylib.ClearBackground(GRAY)
                for y = 1, img.General.height do
                        for x = 1, img.General.width do
                                local key = "x" .. x .. "y" .. y
                                local hex = img.Picture[key] or "ff00ff"

                                raylib.DrawPixel(x - 1, y - 1, hex)
                        end
                end
        raylib.EndDrawing()
end

Now this is good enough for most things, but there are some things you should take into account when you are making an image viewer for INP files. First of all, there are no comments in the INI files. So ; or # will not work within the files, so you cannot have something like x1y1=0f0f0f ; A nice dark shade of grey. The second thing about the files is that sections cannot be padded with spaces, so you cannot have [ General ] or x1y1 = ff0000. Not having spaces increases the simplicity of the INI parsing that needs to be done, since it filters out you having to take spaces into account, so you only have to worry about newlines (\n).

Anyways, that should be it for the normal talk. So here is a list of variables that can be found in the General section of an INP file.

  • width - How wide the image is in pixels. Mandatory.
  • height - How tall the image is in pixels. Mandatory.
  • background - The color of the background if there are any missing pixels or transparency stuff. Optional.
  • alpha - Enable with alpha=1. Enables the alpha part of the color hex, eg. x1y1=ff0000ff. Optional.
  • name - The name of the image itself. Useful for artworks. Optional.
  • note - A note for the image itself. Optional.
  • creator - The creator of the image. Useful for art and photography. Optional.
  • date - The creation date of the image or what the image is of. Useful for photography or art. It is a free-text field, meaning you can put whatever you want in there in whatever format you want. Optional.
  • location - The location the image was taken. Useful for real life photos. Optional.

Afterword

Just some things that I wasn't sure where to put. One thing I realized while writing this spec was that the size of the images wouldn't be that great, since there's no compression to them. To keep simplicity in the format, I think it would be good for you to compress the images, then do something like xzcat image.inp.xz | inpview -. Just a thought to how you could do it. Oh yeah on the topic on viewers, it would probably be a good idea to have an option in your image viewer that lets you take in pictures from stdin, so you can do things like that for compression.

Some things that inspired me to make INP was, well INI files, but also other image formats such as XPM and PBM, since they are also very simple image formats that use plain text to show pictures. Strangely, I kept thinking about the programming language Brainf*ck, since I heard that it was made to be as simple as possible to write a compiler/interpreter for, but really hard to write in. This analogy does not make sense for INP files, since they are easy to make themselves, and easy to make programs for.

If you are making an image viewer that uses this, if there are any missing pixels within the image itself, what I think you should do is warn the user, and still show the picture, but replace the missing pixels with bright pink ones, a la the Source Engine and Minecraft. Another approach you could take is that you could randomly select one of the surrounding pixels around the missing pixel, and just copy it over to the missing one. Or you could just do nothing. I don't know, I'm not your dad, do as you want.

Amendment 1

The first amendment to this spec, only like 3 hours after the first spec was finished.

What is the first amendment to the INP spec, you might be wondering. Well it's to do with color. I was converting a few images from PNG to INP, when I realized that one of the images was only shades of black and white. I thought about this, and I realized that it would be very inneficient to have all 6 (8 if you have alpha enabled) characters, when it could only be 2 characters for 256 colors, or shades of gray. Here is the function that was added to the INP spec.

colors - The amount of colors to use. Options for this are the following:

  • 16bit - The default 16-bit color, that uses 6 characters. Alpha is supported.
  • 256color - 256 color, uses 2 characters, from 00 to FF. Alpha is not supported.
  • 256gray - 256 shades of gray. Uses 2 characters, from 00 to FF. Alpha is not supported.
  • 16color - 16 colors. Uses 00 to 10. Alpha is not supported.
  • 16gray - 16 shades of gray. Uses 00 to 10. Alpha is not supported.
  • bw - Black and white. Litterally 0 or 1. Alpha is not supported.

colors is optional, and if it is not set, it will use the default 6-8 character color encoding.

But vmunix! How are you supposed to handle the color palettes for the lower colors?

Do not fret, I have an idea. For my converter, img2inp, I will first implement the default VGA 256 color palette. Once I have that ironed out, I will then try to implement getting the most common colors from an image, then using that for the colors, and this will be extended down to 16 colors as well. Both options will be available through flags. For the greyscale images, I will try to dither. Dither, dither, dither.

And that brings me to the other function added to INP files. If there is 256 color or 16 colors specified, there will be a new section opened up, [Palette]. Within the [Palette] section, there will be c1 through c255, or c1 through c16 for 16 color. How it will work is that if you were to use color FF in the [Picture] section, it will get mapped to the color defined by c255 in [Palette].

Broken files

If an INP picture has 16 colors specified, but there is up to c255 in the [Palette] section, then just ignore the rest of the colors past 16. If 256 colors is specified, but there is only up to c16, then throw an error and exit. If there is a [Palette] section in a color format that doesn't have the [Palette] section opened up, then ignore it. If alpha is enabled on a color palette that doesn't support it, then ignore alpha. Finally, it should go without saying, but if any of this occurs, then alert the user.
